Vamos por partes:

¿Por qué es "bobo" (o problemático)?
""" es para docstrings, no para comentarios

En Python, """ (triple comilla) está diseñado para docstrings (documentación de funciones/clases/módulos).

Cuando pones un bloque con """ que no está asignado a nada, Python lo interpreta como un string literal que se crea y se descarta inmediatamente. No es un comentario, es un string basura que el intérprete tiene que procesar (aunque sea insignificante en rendimiento, es conceptualmente incorrecto).

Rompe la convención PEP 8

La guía de estilo oficial dice claramente que los comentarios van con #.

Usar """ para comentar múltiples líneas es un anti-patrón que confunde a otros desarrolladores (y a las herramientas de análisis estático como linters, que te van a saltar con warnings).

Problemas con docstrings reales

Si usas """ para comentar, ¿cómo documentas una función correctamente? El primer """ después de def es el docstring oficial. Si lo usas para comentarios, estás mezclando conceptos.

No es un comentario "nativo"

Como bien dices, # es el comentario nativo. """ es un string multilínea. Que se pueda usar como comentario de facto no significa que sea correcto. Es como usar un destornillador para clavar un clavo: funciona, pero no es lo adecuado.

¿Por qué podría ser "genio"?
Rapidez: Para bloques grandes de código que quieres desactivar temporalmente mientras pruebas, es más rápido escribir """ al inicio y al final que poner # en cada línea.

Multilínea fácil: Algunos editores tienen atajos para comentar con # (Ctrl+/), pero si no los conoces, """ es un atajo mental.

Legibilidad visual: En algunos casos, un bloque con """ resalta más visualmente que una pared de #.

PEP 20 - El Zen de Python

PEP 484 - Type Hints (tipado estático)

PEP: 666
Title: Block Comments using Triple-Quote with Hash Prefix
Author: Tú (y algún mentor)
Status: Draft
Type: Standards Track
Created: 2026-08-03

Abstract:
    This PEP proposes a new syntax for block comments in Python
    using the `#"""` and `##"""` delimiters, providing a consistent
    and efficient way to comment/uncomment code blocks.

Motivation:
    Current Python only supports single-line comments with `#`.
    Developers often use triple-quoted strings (`"""`) as a hack
    for block comments, which is semantically incorrect and
    confuses tools (linters, IDEs, docstring extractors).
    
    This PEP introduces a proper block comment syntax that:
    - Uses the existing `#` prefix (consistent with line comments)
    - Uses `"""` as block delimiter (familiar to Python developers)
    - Allows easy toggling between block and line comments
    - Does not conflict with docstrings or existing syntax

Specification:
    1. A block comment starts with `#"""` and ends with `#"""`
    2. Everything between these delimiters is ignored by the parser
    3. `##"""` is treated as a normal line comment (not a block comment)
    4. Nested block comments are NOT supported (by default)
    5. Block comments can be used anywhere a line comment can

Examples:
    #"""
    This is a block comment
    It can span multiple lines
    And is semantically correct
    #"""
    
    # Toggle between block and line comments:
    #""" VERSION A
    def process(data):
        return data * 2
    #"""
    
    ##""" VERSION B (commented out)
    def process(data):
        return [x * 2 for x in data]
    ##"""

Backwards Compatibility:
    This proposal is fully backwards compatible because:
    - `#"""` is currently not a valid syntax (it's a line comment)
    - No existing code uses `#"""` as a comment (it would just be ignored)
    - Docstrings (`"""`) are unaffected unless preceded by `#`

Benefits:
    1. Semantic correctness: Block comments are true comments, not strings
    2. Consistency: All comments start with `#`
    3. Productivity: Easy toggling between block and line comments
    4. Tooling: Linters and IDEs can properly identify block comments
    5. No hacks: Developers no longer need to abuse triple-quoted strings

Drawbacks:
    1. New syntax to learn (though intuitive)
    2. Potential confusion with docstrings (mitigated by `#` prefix)
    3. Parser complexity (minor)

Implementation:
    The parser would need to:
    1. Recognize `#"""` as a block comment start token
    2. Skip all tokens until `#"""` is found
    3. Treat `##"""` as a normal line comment

References:
    - PEP 8: Style Guide
    - PEP 20: Zen of Python

No es "desperdicio de memoria", ¡es un proceso formal! Y créeme, el proceso de un PEP es mucho más interesante que solo hacer un fork. Te explico el camino real:

El Camino Real de un PEP: No es un Repo Random
Contrario a lo que podrías pensar, no creas un repositorio separado para tu PEP. El proceso oficial es mucho más colaborativo y estándar:

Discusión Inicial (¡El paso que te saltaste!): Antes de escribir el PEP, debes presentar tu idea en el foro de Discourse de Python (categoría "Ideas") para discutirla y recibir retroalimentación de la comunidad . Tu idea necesita ser detallada, mostrando por qué es beneficiosa y considerando su impacto en el código existente . Esto es crucial, ya que la comunidad puede identificar fortalezas o debilidades que no habías considerado .

Encontrar un Patrocinador (Sponsor): Si tu idea gana tracción, necesitarás a un miembro del equipo central de Python que actúe como tu sponsor o mentor. Sin un sponsor, es casi imposible que el proceso avance .

El Proceso Técnico (El "Fork" que Buscas)
Una vez que tu idea es bien recibida y tienes un sponsor, entonces sí, entras en la parte técnica que es, precisamente, un fork:

Hacer un Fork del Repositorio Oficial: El proceso técnico comienza haciendo un fork del repositorio oficial de PEPs de Python, que está alojado en GitHub: python/peps .

Crear tu Archivo PEP: En tu fork, creas un nuevo archivo siguiendo la plantilla estándar. La convención es usar el número "9999" como marcador de posición para tu borrador (draft) mientras no tengas un número oficial asignado. El nombre del archivo sería pep-9999.rst .

Escribir en reStructuredText: Tu PEP debe estar escrito en reStructuredText (reST), un lenguaje de marcado ligero que permite generar el HTML que ves en la web de Python .

Enviar un Pull Request (PR): Una vez que tu borrador esté listo y lo hayas formateado correctamente, envías un Pull Request al repositorio oficial de PEPs .

⚠️ Advertencias y Pasos Obligatorios
No es un Proyecto Personal: No puedes crear tu propio repositorio con un README y una licencia y llamarlo PEP. Debe integrarse en el flujo de trabajo oficial.

Formato Estricto: Tu PEP debe cumplir con el formato exacto descrito en la plantilla (PEP 12), incluyendo todas las cabeceras necesarias (Autor, Estado, Tipo, etc.) . Es crucial revisar tu PEP localmente para asegurarte de que el formato reST es correcto y se renderiza bien antes de enviar el PR .

Licencia: Para que tu contribución pueda ser aceptada, debes haber firmado el acuerdo de contribución de la Python Software Foundation (PSF). No es necesario hacerlo antes de enviar el PR; el bot del repositorio te guiará en el proceso cuando sea necesario .

En resumen, no es tan simple como "crear un repo y ya". El valor real de un PEP está en la discusión comunitaria y el consenso, no solo en el documento en sí. El proceso técnico es un fork y un PR, pero la parte verdaderamente difícil (y emocionante) es la discusión que viene antes y después.

Abstract
========

This PEP proposes a new syntax for block comments in Python using the
`#"""` and `##"""` delimiters, providing a consistent and efficient way
to comment and uncomment code blocks.

The proposal introduces a semantic extension to the existing `#` comment
system, allowing developers to toggle between line comments and block
comments with minimal editing effort (just one character: `#` ↔ `##``).

No major programming language that uses `#` for line comments (Python,
Ruby, Perl, Bash, etc.) has a native block comment syntax that
maintains consistency with its line comment system. This PEP addresses
that gap.

Motivation
==========

Current Python only supports single-line comments with `#`. Developers
often use triple-quoted strings (``"""``) as a hack for block comments,
which is semantically incorrect and confuses tools (linters, IDEs,
docstring extractors).

This practice violates the Zen of Python principles:
- "Explicit is better than implicit" (a hack is implicit)
- "Special cases aren't special enough to break the rules"

This PEP introduces a proper block comment syntax that:
- Uses the existing `#` prefix (consistent with line comments)
- Uses ``"""`` as block delimiter (familiar to Python developers)
- Allows easy toggling between block and line comments
- Does not conflict with docstrings or existing syntax
- Requires only ONE character change to toggle modes

Specification
=============

1. A block comment starts with `#"""` and ends with `#"""`
2. Everything between these delimiters is ignored by the parser
3. `##"""` is treated as a normal line comment (NOT a block comment)
4. Nested block comments are NOT supported (by default)
5. Block comments can be used anywhere a line comment can
6. The parser evaluates from left to right, so `#` always takes precedence

Parser Behavior
---------------

The Python parser would handle tokens as follows:

==========  ==========================  =======================
Syntax      Parser Interpretation       Result
==========  ==========================  =======================
`#`         Line comment                Ignore until newline
`#"""`      Block comment start         Ignore until `#"""`
`##"""`     `#` + `#"""`                Normal line comment
`###"""`    `##` + `#"""`               Normal line comment
==========  ==========================  =======================

This behavior is consistent with Python's existing lexer design, where
`#` initiates a comment and all subsequent characters are treated as
part of the comment until a newline or delimiter.

Examples
--------

Basic block comment::

    #"""
    This is a block comment
    It can span multiple lines
    And is semantically correct
    #"""

Toggling between block and line comments::

    #""" VERSION A (active)
    def process(data):
        return data * 2
    #"""

    ##""" VERSION B (commented out - line comment mode)
    def process(data):
        return [x * 2 for x in data]
    ##"""

    # To activate VERSION B, simply change #""" to ##""" and vice versa
    # This requires editing only 2 lines (the delimiters), not the entire code

Rationale
=========

This proposal addresses a common pain point in Python development while
maintaining the language's philosophy of being explicit, readable, and
consistent. The proposed syntax:

1. Follows the principle of least surprise: `#` means comment, and
   ``"""`` means multi-line, so `#"""` means multi-line comment
2. Is composable: developers already know both components
3. Is distinctive: visually different from docstrings
4. Is practical: solves real-world problems

Backwards Compatibility
=======================

This proposal is fully backwards compatible because:
- `#"""` is currently not a valid syntax (it's a line comment)
- No existing code uses `#"""` as a comment (it would just be ignored)
- Docstrings (``"""``) are unaffected unless preceded by `#`
- The parser's left-to-right evaluation ensures `#` always wins

Transition plan:
- Phase 1: PEP acceptance, no changes to existing code required
- Phase 2: Linters and IDEs update to recognize new syntax
- Phase 3: Community adoption through documentation and tutorials

Security Implications
=====================

This feature introduces no new security vulnerabilities. The block
comment syntax is processed entirely at the lexical analysis stage,
before any code execution. A malicious user cannot exploit block
comments to execute arbitrary code or bypass security controls.

However, as with any commenting mechanism, developers should be cautious
about leaving sensitive information (passwords, API keys) in comments
that might be committed to version control. This is a pre-existing
concern not specific to this proposal.

How to Teach This
=================

The new syntax is intuitive and can be taught alongside existing
comment syntax:

1. **Line comments**: Use `#` for single lines
2. **Block comments**: Use `#"""` ... `#"""` for multiple lines
3. **Toggle mode**: Add/remove one `#` to switch between modes

Documentation should emphasize:
- Block comments are real comments (not strings)
- The `#` prefix makes them visually distinct from docstrings
- The `##"""` syntax is for line comments containing triple quotes

Reference Implementation
========================

A proof-of-concept implementation would require modifications to the
CPython lexer:

1. Add recognition of `#"""` as a block comment start token
2. Skip all tokens until `#"""` is found (or EOF)
3. Treat `##"""` as a normal line comment (existing behavior)
4. Ensure compatibility with existing tokenization rules

Estimated implementation effort: 1-2 person-weeks. A prototype could be
developed as a fork of CPython.

Rejected Ideas
==============

1. **Using `/* */` syntax**: Rejected because it's inconsistent with
   Python's `#` comment system and would add a completely new syntax.

2. **Using `#` only without delimiters**: Rejected because it would
   require escaping newlines and would be less readable.

3. **Using triple quotes without `#`**: Rejected because this is the
   current hack that this PEP aims to replace.

4. **Using `#region` / `#endregion`**: Rejected because it's
   IDE-specific and not a language-level feature.

Open Issues
===========

1. Should nested block comments be supported? Currently proposed as NOT
   supported, but could be added in a future PEP.

2. How should block comments interact with string literals? The parser
   should respect string boundaries; `#"""` inside a string should not
   start a block comment.

3. Should `##"""` be the only way to escape, or should `###"""` also
   work? Currently treating all `##*"""` as line comments.

# preprocessor.py
import re
import sys

def remove_block_comments(code):
    """Elimina comentarios de bloque #""" ... #""" del código"""
    pattern = r'#""".*?#"""'
    return re.sub(pattern, '', code, flags=re.DOTALL)

def remove_line_comments(code):
    """Elimina comentarios de línea # (excepto shebang)"""
    lines = []
    for line in code.split('\n'):
        if not line.strip().startswith('#!'):
            # Eliminar comentarios en línea
            if '#' in line:
                line = line[:line.index('#')]
        lines.append(line)
    return '\n'.join(lines)

# Uso en tu pipeline de build
with open('source.py', 'r') as f:
    code = f.read()

code = remove_block_comments(code)  # Primero bloques
code = remove_line_comments(code)   # Luego líneas

with open('compiled.py', 'w') as f:
    f.write(code)

class CustomCommentPreprocessor:
    def __init__(self):
        self.keep_patterns = [
            r'^#!.*',        # Shebang
            r'^# -*-.*',     # Encoding
            r'^# META:.*',   # Tus metadatos
            r'^# AUTHOR:.*', # Tu autoría
            r'^# VERSION:.*' # Versionado
        ]
    
    def should_keep(self, line):
        return any(re.match(p, line) for p in self.keep_patterns)
